# Independent licensing and feedback review

Reviewed November 8, 2026. **PASS for internal consistency, with artwork-rights questions explicitly unresolved.** This review checked LICENSE, LICENSING.md, RIGHTS.md, the study-directory notice, CONTRIBUTING.md, issue forms/configuration, feedback policy workflow, app feedback links and relevant public research wording. No permissions requests or external messages were sent.

## Licensing

- LICENSE contains the standard MIT terms with RJ Andrews' 2026 notice. LICENSING.md limits that grant to original software and identifies the covered code areas. Its separate CC BY 4.0 grant applies only to the project's original research contribution and only to rights the project holds.
- Both grants exclude the underlying artworks, SVG artwork representations and third-party material. RIGHTS.md and the study-directory README repeat that boundary. Mixed JSON containers are expressly not treated as a grant of every source field. The data grant does not claim ownership of bare facts.
- The public wording does not claim that criticism, research, vectorization, attribution, a disclaimer or an open software license guarantees fair use. It does not claim that estate permission has been obtained. The rights review identifies public display and downloadable vector reuse as distinct unresolved uses.
- The app's recolored SVG export adds an interpretation/rights notice and a primary citation rather than assigning MIT or CC BY to the resulting artwork study. This is consistent with the asset exclusion. It is an attribution/scope notice, not a clearance mechanism.
- I amended docs/RIGHTS-REVIEW.md to replace its earlier proposed/optional licensing language with the MIT and limited CC BY grants now actually adopted through LICENSE and LICENSING.md. That amendment does not change the unresolved artwork-rights assessment.

No broken local Markdown targets were found in the reviewed licensing/contribution documents. The scholarly context distinguishes a reading list from endorsement or consultation; its treatment of interpretive comparison remains qualified and evidence-based.

## Feedback policy and actual enforcement

- The app opens a GitHub issue form with a work ID/source URL/page URL; it does not hold a write credential or submit an issue itself. The visitor reviews and submits through GitHub.
- Both forms explicitly require personal submission and warn that the issue is public. The work form preserves the distinction between evidence and suggestions and asks users not to upload copyrighted photographs or private information.
- Blank issue creation is disabled in the normal web interface. The workflow closes newly opened/reopened issues when GitHub marks the author as a Bot or the login ends in `[bot]`. It uses only the issue-update operation and does not run issue-body code. Its permissions are limited to issue writing.
- These mechanisms are friction and recognizable-bot handling, not proof of a human. They do not block an agent operating a User account or all API submissions. CONTRIBUTING.md states this limitation plainly and does not promise bot-proof feedback. No stronger identity or anti-bot service has been claimed.

A private rights discussion would require the repository owner to provide a private channel when requested; the issue form itself is public. The current warning not to post confidential details is appropriate. This is an operational limitation, not a promise that GitHub issues provide private intake.

The user-authorized publication decision remains separate from this consistency pass: licenses clarify the project's own grants, while the artwork representation permissions/fair-use basis remain unresolved as documented in docs/RIGHTS-REVIEW.md.
